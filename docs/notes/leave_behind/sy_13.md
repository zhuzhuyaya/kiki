# 属主校验：防横向越权

> 传承人只能操作自己名下的资源。`@SaCheckRole` 挡"没身份的"，属主校验挡"有身份但越界的"——两层防线，缺一不可。

## 两种越权

- **纵向越权**：低角色调高角色接口 → 靠 RBAC（`@SaCheckRole`）防
- **横向越权**：同角色用户操作**别人的**资源 → 靠属主校验防。前端藏住按钮没有任何用，接口必须自己校验

## getMyCourse 模式

所有"单资源操作"（开场次、看场次、改封面……）都先过这个口子：

```java
/**
 * 取"属于自己的"课程：不存在、或存在但不是你的，统一报"课程不存在"。
 */
private Course getMyCourse(Long courseId) {
    Inheritor inheritor = inheritorService.currentInheritor();
    Course course = courseMapper.selectById(courseId);
    if (course == null || !course.getInheritorId().equals(inheritor.getId())) {
        throw new BusinessException("课程不存在");
    }
    return course;
}
```

两个讲究：

1. **校验收口在一个私有方法**——新接口直接复用，不会漏。第 4 课下半场的"设置封面"新功能，一行 `getMyCourse(courseId)` 就自动获得了防护，这就是收口的回报
2. **"不是你的"和"不存在"返回同一句提示**。如果对别人的 courseId 返回"无权访问"，攻击者立刻知道这个 id 存在，可以遍历探测；统一报"不存在"就没有信息泄露。和登录失败不区分"账号不存在/密码错误"是同一个思想

## 双层越权实测

同一个接口 `POST /inheritor/courses/{B的课程id}/sessions`：

| 攻击者 | 结果 | 拦截层 |
| --- | --- | --- |
| 用户 C（未入驻，USER 角色） | 403 | `@SaCheckRole("INHERITOR")` 角色层 |
| 用户 C（已入驻，INHERITOR 角色） | `{"code":400,"msg":"课程不存在"}` | `getMyCourse` 属主层 |

| 防线 | 挡什么 | 在哪 |
| --- | --- | --- |
| RBAC | 没有角色的 | 拦截器 + `@SaCheckRole` |
| 属主校验 | 有角色但越界的 | service 私有方法 |

## REST 参数分工惯例

```java
@PostMapping("/{courseId}/sessions")   // 资源 id 放路径
public Result<Void> addSession(@PathVariable Long courseId, ...) 
```

- **路径**：资源定位（`{courseId}` 用 `@PathVariable` 绑定）
- **查询参数**：筛选/分页（`?page=1&status=0`，配 `@RequestParam(defaultValue=...)`）
- **请求体**：业务数据（DTO + `@Valid`）

## 顺手记两个校验注解

开课时间用 `@Future(message = "开课时间必须在未来")`——bean validation 自带的时间注解，一个注解省一段 if。同类还有 `@Past`、`@PastOrPresent`。

## 小结

- 横向越权是接口层的事，前端藏按钮不是防护
- 资源操作先过属主校验，收口成一个方法
- 不存在/不属于统一话术，不给探测空间
- 两层防线各自工作：先角色后属主，测试时两层都要打
